# LanAudioStream —— 局域网纯音频串流（Windows → Android）

把 Windows 11 正在播放的**系统声音**，以低延迟、高质量的方式串流到同一局域网的 Android 手机上播放。
桌面端基于 **WASAPI Loopback** 抓取系统混音，**Opus** 编码，通过自研 **UDP 协议（LAS1）** 传输；
手机端用 **AudioTrack** 播放，实时绘制延迟/码率/速度/丢包/抖动曲线，并在本机统计左右声道响度电平。

```
┌─────────────────────── Windows 11 桌面端 ───────────────────────┐
│ WASAPI Loopback ─► 48kHz/2ch float ─► Opus(10ms) ─► UDP 47655  │
│   ▲ 可选静音本机扬声器（串流不受影响）                          │
└────────────────────────────┬────────────────────────────────────┘
                             │  UDP（同一局域网，无服务器中转）
┌────────────────────────────▼────────────────────────────────────┐
│ 发现(47654 广播) ─► 握手 ─► 抖动缓冲 ─► Opus 解码 ─► AudioTrack │
│ 后台前台服务 + 实时曲线（位于设置界面上方）                      │
└─────────────────────────────────────────────────────────────────┘
```

## 1. 功能一览

### 桌面端（Windows 11）
- 捕获**系统播放音频**（WASAPI Loopback，事件驱动，10–20 ms 缓冲，可运行于静音状态）
- **可关闭本机扬声器输出**：调用 `IAudioEndpointVolume::SetMute`，采集端不受影响（已实测验证，见 §5）
- 状态面板：监听状态、客户端 IP、会话状态、发送码率/包速率/累计流量
- 运行状态**只显示本机可直接得到的指标**（客户端、会话状态、当前编码、采集设备、采集+编码延迟、发送码率/包速率/累计发送）；
  已移除全部需要手机回传的显示项，也移除了采集电平条
- **设置手动提交**：改动只改本机界面，点「保存设置」才生效并同步到手机端；「重置所有设置」一键恢复默认值
- 码率 64–320 kbps、帧长 5/10/20/40 ms、抗丢包冗余开关、端口可配
- 已移除实时曲线图与低延迟模式开关，减少桌面端 CPU 占用
- UDP 广播自动发现（无需输入 IP），设备名显示为 `LanAudioStream@计算机名`
- 内置 headless 自检模式与协议测试客户端（LoopbackClient.exe）

### 手机端（Android 8.0+，APK ~0.8 MB）
- **自动发现 + 自动连接**，断线指数退避重连（300 ms → 4 s）
- **后台播放**：前台服务 + 通知栏实时指标 + WakeLock/WifiLock/MulticastLock
- 实时指标：端到端延迟、抖动、接收码率、**实时速度(KB/s)**、丢包率、丢包/丢帧数、
  抖动缓冲、音频输出缓冲、已解码帧、PLC 补偿、播放欠载、时钟同步 RTT
- **实时曲线图位于设置界面上方**（自绘 Canvas，5 条曲线，无第三方依赖）：按屏幕刷新率（60/90/120Hz）绘制、
  中点二次贝塞尔平滑、数据用环形缓冲无装箱，数据每 500ms 更新也能连续平滑滚动
- **左右声道响度电平条（L / R）**：本机从解码后的 PCM 统计（不依赖电脑端回传），同样按刷新率绘制，
  快启慢落弹道 + 峰值保持，高帧率下不漏瞬态
- **设置改为手动保存**（改动只改本机界面，点「保存设置」才下发；本机播放设置改动即时生效）：
  - 电脑端生效项：音频格式（Opus / **PCM 无损**）、采样率 48/44.1/32/24/16 kHz、编码码率 64–320 kbps、
    帧长 5/10/20/40 ms（PCM 上限 10 ms）、声道 立体声/单声道、抗丢包冗余、静音电脑扬声器、
    采集缓冲 10–50 ms、静音省流 DTX
  - 本机生效项：**断连超时**（3–600 s）、抖动缓冲策略（自动/延迟优先/稳定优先）、断线自动重连、**指标刷新率**（1–60 Hz）、通知栏指标开关
- 「重置所有设置」一键恢复默认值，再点「保存设置」即可同步给电脑端
- **连接后自动停止探测**：桌面端停止周期广播、手机端停止发送探测包，断线后自动恢复（省电、少唤醒 WiFi）
- 已移除低延迟模式开关与播放音量调节；输出固定为默认媒体路径（约 80 ms 缓冲，保留杜比/均衡器等系统音效）
- 服务器列表（多桌面端时可手动选择连接）

## 3. 快速开始

### 3.1 桌面端

从 **[Releases](https://github.com/XiaoliuNya/LanAudioStream/releases/latest)** 下载 `LanAudioStream-1.0.0-win-x64.exe`（自包含单文件，无需安装 .NET），直接双击运行。

或从源码自行构建（需 .NET 10 SDK）：
```powershell
scripts\build_desktop.ps1
# 产物：dist\LanAudioStream-1.0.0-win-x64.exe
```
1. 选择“默认播放设备（推荐）”
2. 需要静音本机时勾选 **静音电脑扬声器**，再点 **保存设置**（静音后继续串流）
3. 点击 **▶ 开始串流**
4. 首次运行如弹出 Windows 防火墙提示，请勾选“专用网络”并允许（或运行 `scripts\allow_firewall.ps1`）
5. 之后每次改完音频设置，点 **保存设置** 才会生效并同步到手机端；点 **重置所有设置** 可一键恢复默认值

### 3.2 手机端

从 **[Releases](https://github.com/XiaoliuNya/LanAudioStream/releases/latest)** 下载 `LanAudioStream-1.0.0.apk`，传到手机点击安装（需允许“安装未知来源应用”），或用 adb：
```powershell
adb install -r LanAudioStream-1.0.0.apk
```
1. 手机与电脑连同一个 WiFi
2. 打开 App → 点击 **开始接收**（App 会自动发现桌面端并连接）
3. 音频参数在「音频设置（在电脑上生效）」里修改，**改完点「保存设置」才会下发**；
   「播放设置（本机）」里的抖动策略/自动重连立即生效，也会随「保存设置」一并同步给电脑端；
   点「重置所有设置」恢复默认值后再保存即可同步。实时曲线图就在设置界面上方

> 桌面端与手机端无需任何手工配对：桌面端每秒广播一次，手机端收到即自动连接。

## 4. 技术方案

| 环节 | 方案 | 说明 |
|---|---|---|
| 采集 | NAudio 3.1 `WasapiRecorder` + `WithLoopbackCapture()` | 事件驱动共享模式，20 ms 缓冲，直接拿到 `float32/48 kHz/2ch`；非 48k/2ch 时自动重采样 |
| 编码 | Concentus（**纯托管 Opus**） | 48 kHz 立体声、`OPUS_APPLICATION_AUDIO`、Complexity 10、VBR、In-band FEC，编码耗时 ≈0.2–0.4 ms/帧 |
| 传输 | 自研 UDP 协议 LAS1 | 无队头阻塞、无重传；单帧一包（10 ms → 100 包/秒）；可选**同包重发上一帧**实现 0 成本 1 级丢包恢复 |
| 时钟同步 | NTP 式四时间戳（`SYNC_REQ/SYNC_RSP`） | 取最小 RTT 样本估计时钟偏移，从而在手机上算出**真实端到端延迟**（仅手机端显示） |
| 抖动缓冲 | 自适应有序播放队列 | 目标缓冲 40–400 ms（欠载自动加大、干净链路缓慢回退、比目标深时主动剪掉最旧帧回落）；已知丢包用 Opus PLC 合成；发送端空闲时写静音但不计欠载；溢出时丢弃最旧帧以锁定延迟 |
| 输出 | `AudioTrack` MODE_STREAM | 默认媒体路径 + 约 80 ms 缓冲（低延迟模式已取消，保留系统音效） |
| 发现 | UDP 47654 广播 + 单播应答 | 手机端 `PROBE`，桌面端 `ANNOUNCE`（含名称、端口、是否正在串流） |
| 保活 | 手机每 100 ms 回传 `RR` | 桌面端超过「断连超时」（默认 8 s，可设 1–600 s）无回传时**只暂停发送、保留会话**，恢复反馈或手机重连后立即继续，不再直接断流 |
| 远程设置 | `SETTINGS`（type=11，TLV） | 只在点「保存设置」时提交 → 接收端校验并应用 → 重发 `HELLO_ACK` 并回推权威状态（连接建立时也推一次） |
| 抖动缓冲 | 自适应（20–180 ms 低延迟 / 60–400 ms 音效） | 欠载自动加大、链路干净缓慢回落；也可由手机固定为「延迟优先/稳定优先」 |

协议细节见 **[docs/PROTOCOL.md](docs/PROTOCOL.md)**。

## 5. 关键设计验证（本机实测）

### 5.1 “静音本机扬声器后仍能采集” 是否成立？
在目标机器（Windows 11 + Senary Audio 默认播放设备）上实测：
先用 `WasapiOut` 播放 440 Hz 正弦，再用 `WasapiLoopbackCapture` 采集并统计 RMS，中途切换系统静音：

| 阶段 | RMS |
|---|---|
| 未静音 | 0.106082 |
| **系统静音后** | **0.106054** |
| 恢复未静音 | 0.106069 |

结论：**端点静音不影响 Loopback 采集**，因此“关掉本机扬声器继续串流”可以原生实现，无需虚拟声卡。

### 5.2 端到端链路实测（本机回环，Released 版）
- 采集：`Senary Audio` / `48000 Hz / 2 ch / 32 bit Extensible(float)` / 缓冲 20 ms
- 播放 1000 Hz 测试音 → 采集 → Opus 128 kbps/10 ms → UDP → 接收端解码写 WAV
- 解码音频分析：**RMS = 0.2017，1000 Hz 幅值 = 0.2836（源信号 0.3）→ 判定“检测到目标频率音频 ✓”**
- 端到端延迟（采集时刻→接收解码时刻，含采集缓冲与编码）：**19–20 ms**
- 网络抖动：**0.09–0.16 ms**；丢包：**0.00%**；编码耗时：0.2–0.4 ms/帧
- C# 接收端与 **Java（APK 内同一份代码）** 解码结果**完全一致**（帧数、RMS、频谱幅值逐位吻合）

## 8. 已知限制

- 手机端与桌面端必须处于**同一可广播的局域网**（部分企业/访客 WiFi 会隔离客户端，此时可改用手机热点或手动连接）。
- 蓝牙耳机/音箱本身有 100–200 ms 固有延迟，非本工具引入；建议用有线耳机评估低延迟效果。
- 桌面端默认播放设备切换后需重新点击“开始串流”（当前未订阅设备变更通知）。
- 单客户端：同一时刻仅一台手机接收（协议可扩展为多播，未实现）。
- 手机端 UI 未做平板/横屏适配（锁定竖屏）。

|---|---|---|

| 安卓端打开即崩溃 | `AndroidManifest.xml` 使用相对类名 `.MainActivity` / `.StreamService`，按 `namespace=com.lasaudio` 解析成 `com.lasaudio.MainActivity`，而真实类在 `com.lasaudio.app` 包下 → `ClassNotFoundException` | 清单改为**全限定类名**；新增构建期「清单类名 ↔ dex」校验与运行时崩溃日志 |
| 安卓端音频周期性断续（≈0.7s 一次） | 接收端抖动缓冲过于激进：目标缓冲≈0、AudioTrack 缓冲只有 20ms，任何抖动立刻补静音，并把在途的包判为「过晚」丢弃（帧冗余也就失效了）；另外 WiFi 省电（新系统上 `WIFI_MODE_FULL_HIGH_PERF` 已基本失效）会带来周期性停顿 | ① 接收端改为**自适应抖动缓冲**（低延迟 20–180ms / 音效 60–400ms，欠载自动加大、链路干净缓慢回落）；② 下一帧未到时，只要音频设备仍有缓冲就继续等（上限 400ms），不急着补静音，保住帧冗余恢复；③ AudioTrack 缓冲提到 60ms / 150ms；④ WiFi 锁改用 `WIFI_MODE_FULL_LOW_LATENCY`（API 29+）；⑤ UDP 接收缓冲提到 1MB |
| 桌面端数据端口被两个实例共用（排查中发现） | 数据 socket 设置了 `ReuseAddress`，两个桌面端实例可同时绑定同一端口并同时向手机发包，听起来同样是「断续杂音」 | 数据端口改为 `ExclusiveAddressUse`，第二个实例直接报错提示端口占用 |

| **无损模式（PCM）一开就崩溃** | 冗余负载缓冲固定为 Opus 上限 1275 字节，而 PCM 10 ms 立体声帧为 1920 字节 → `Span.CopyTo` 抛 `ArgumentException`，异常发生在发送线程上，.NET 会直接结束进程 | 冗余缓冲改为 8 KB 上限、超长时自动放弃冗余而不是抛异常、发送路径整体加 try/catch 并把异常计数暴露到界面与日志 |
| 采集时间戳按「帧数」而非「样点数」换算（排查中发现） | 帧长改为 5 ms 或采样率变化后，桌面端 `captureUs` 只按 20.8 µs/帧 前进，手机端算出的延迟以 ~1 s/s 漂移（曾出现 3.5–10 s 的假延迟） | 改为 `帧数 × 每帧样点数 ÷ 采样率`；同时帧长/采样率变化时重置采集时间基准 |
| PCM 无损模式先期不可用（排查中发现） | `JitterPlayer` 的播放循环在 `decoder == null` 时直接跳过，而 PCM 模式本就不需要 Opus 解码器；另外 PCM 需要更大的单包缓冲 | 播放循环放开该判定、PCM 直通解码（字节→16bit 采样）、单包上限提升到 8 KB、PCM 自动关闭帧冗余 |
| 采集电平显示恒为 0（排查中发现） | 电平计数复用了会因饥饿被重置的帧计数器 | 独立电平计数器 |
| 桌面端数据端口被两个实例共用（排查中发现） | 数据 socket 设置了 `ReuseAddress` | 改为 `ExclusiveAddressUse`，第二个实例直接报错 |

现场排障：APK 内置未捕获异常记录器（写入 `Android/data/com.lasaudio/files/crash-*.txt` 并 Toast 提示），
Service 初始化与前台启动均加了保护，避免单点异常直接杀掉应用。

| 项 | 变更 |
|---|---|
| **欠载不再被「丢包」误触发** | 之前 PLC（丢包补偿）也计入自适应计数：丢一个包就把目标缓冲 +20 ms 且极难回落，延迟只涨不降。现在**只有真正饿死（补静音）才加缓冲**，步长 10 ms、干净 6 秒即回落 10 ms。出口 JVM 实测：44 次 PLC 事件后目标缓冲保持 60 ms 不变 |

### 10.6 第四轮：按现场日志修「成串交付」

现场日志（手机端界面日志）：

   网络停顿 249ms（停顿后 30ms 内 26 包突发，累计 45 次）
   网络停顿 255ms（停顿后 30ms 内 27 包突发，累计 46 次）
   网络停顿 286ms（停顿后 30ms 内 30 包突发，累计 48 次）

250 ms 里「理论上」应有 25 个包，随后 30 ms 内正好冲出 25~30 个 → **一个都没丢，只是被整段延迟交付**
（典型是 WiFi 省电/DTIM 把包压在 AP 里，或接收线程被卡住 250 ms 后内核一次性吐出来）。此前缓冲只有 40~60 ms，
每次停顿必然补静音 → 听感就是"每几秒卡一下"。

| 项 | 变更 |
|---|---|
| **按停顿自动加深缓冲** | 新增 `noteArrivalGap(gapMs)`：只要观察到 > 60 ms 的到达停顿，就把目标缓冲设为 `停顿 + 50 ms`，上限从 300 提到 **400 ms**。JVM 实测：250 ms 停顿 → 目标 60→300 ms |
| 不「刚加深就回落」 | 只有**连续 30 秒没有停顿**才允许回落（每次 −10 ms），否则保持当前深度；长时间干净后逐步忘掉历史停顿 |
| 实时速率显示 | 与其它指标**同款文本框**（无自绘、无进度条）：数值取接收线程按 **滑窗结算的真实值**，窗口长度＝指标刷新周期（见 §10.7），所以数字随指标刷新率一起变，不会每秒才跳一次（不做平滑） |
| 设置确认提示 | 之前一直停在「等待电脑端确认…」：界面只更新了控件、没有更新提示。现在电脑端每次回推设置后显示 `电脑端已确认设置 ✓`；4 秒内没有回执则提示「未收到电脑端确认」 |
| 去重表零分配 | `LinkedHashSet<Long>` → 原始 `long` 环形表，去掉收包路径最后一点装箱分配 |

### 10.7 速率原始数据与指标刷新率同频

| 项 | 变更 |
|---|---|
| 码率/实时速度的**原始数据** | 之前接收线程按**固定 1 秒窗口**结算，指标刷新率调到 10 Hz 也只是把同一个数字重复画 10 次（曲线上的码率/速度实为 1 Hz 阶梯）。现改为按到达时间记录的**滑窗**（`StreamClient.pushRateSample`）：窗口长度＝指标刷新周期（`AppState.metricsIntervalMs()`，夹取 50–1000 ms），**每收到一个包就用最新窗口结算一次**，因此界面每次刷新取到的都是新值，曲线不再是一秒一格 |
| 静音/低包速保护 | 窗口内包数 < 2 时按 2 倍自动放宽（最多 1 秒），避免 DTX 静音期（每 100 ms 才一个包头包）在短窗口下于 0 与真值之间乱跳；实际使用的窗口与包数可从 `RxStats.rateWindowMs / rateSamples` 读到（JVM 自检：`CoreProbe client --rate-window 200 --print-ms 200`） |
| 分母 | 会话刚开始、窗口还没被数据填满时，用**真正经过的时间**做分母，避免首个窗口被低估 |
| 口径不变 | 码率含包头与冗余、速度只算音频负载；超过 2 秒没有任何音频包时仍归零 |
| 上限 | `AppState.metricsIntervalMs()` 仍有 50 ms 下限（≥20 Hz 的设置会被夹到 20 Hz），故窗口最短 50 ms；要真正跑到 60 Hz 需另行调整该下限 |

实测（本机回环，10 ms 帧长，窗口 200 ms）：串流期间每 200 ms 一行，码率 205–238 kbps、速度 14.8–15.2 KB/s 逐行变化；
测试音停止后窗口内即刻回落（134→136 kbps、15.2→1.0 KB/s），不再像 1 秒窗口那样滞后一秒。

### 10.8 第五轮：延迟与稳定性的系统性修复（含实测对比）

本机回环实测（10 ms 帧长 / 128 kbps，`CoreProbe client --csv` 每秒采样一次）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 干净链路稳态端到端 | **216 ms**（队列 170 ms / 目标 60 ms，纹丝不动） | **79–94 ms**（队列 30–60 ms，向目标收敛） |
| 停播 10 秒后再播放 | **576 ms**（目标被顶到 400 ms 上限，25 秒不回落） | **91 ms**（目标 40–60 ms，不回落） |
| 静音期间的"欠载"计数 | 每秒 +100（虚高，并驱动缓冲加深） | **0**（只计 idleSilenceFrames） |

| 问题 | 根因 | 修复 |
|---|---|---|
| **抖动队列只涨不落**（延迟永久变高） | 溢出裁剪分支里 `k >= expectedSeq` 对队列中的帧恒为真而 break，等于永不裁剪；播放按绝对时刻表推进，`scheduleUs = nowUs` 只把积压搬进设备管道 | 溢出时真正丢掉最旧的未播帧并前移 `expectedSeq`；新增按队列深度（队列+设备）与目标比较的**主动剪接回落**（`DRAIN_MARGIN_MS=40`、最快每秒一次） |
| **停播/静音把缓冲顶到 400 ms** | `noteArrivalGap` 把任何 >60 ms 的到达空档都当网络停顿，而 PC 停止放声音时发送端直接不发包 | 停顿先记 pending，只有"停顿后仍有包持续到达"才确认加深；空档 >600 ms 直接忽略 |
| **静音被计成欠载** | 缺帧一律走欠载分支，DTX 标记每 100 ms 才一个 | 新增"发送端空闲"判定（>250 ms 无任何包或处于 DTX 段）：只写静音，计 `idleSilenceFrames`，不计欠载、不驱动自适应 |
| **设备缓冲计量失真**（一次停顿后恒为 0） | `playbackHeadPosition` mask 成 32 位后与累计写入量相减，重锚条件是"领先 1 秒"；48 kHz 连续播放 24.8 h 还会回绕 | 改为对播放头取**增量累加**（差值按 32 位无符号解释，天然跨回绕） |
| 等晚到帧（帧冗余恢复）从不生效 | `MIN_DEVICE_BUFFER_MS=25` 大于设备稳态深度（约 1 帧=10 ms），判定恒真 | 门槛降到 6 ms，让"设备还有 ~10 ms 就先等一等"真正生效 |
| **44.1 / 32 kHz 直接杀进程**，并把坏值写进 settings.json | 两端 UI 都提供非法的 44.1/32 kHz，管线只做 `Clamp(8000,48000)`，`new OpusEncoder(44100,…)` 抛 ArgumentException | UI 预设改为 8/12/16/24/48 kHz；管线按"就近合法档"归一化（44.1→48、32→24）；保存路径加 try/catch 并提示；`AppSettings.Save` 回传失败原因 |
| **帧长双源不一致**（上报 60 ms / 实际编 40 ms） | UI 夹取 2–60，管线夹取 5–40，HELLO_ACK 用 `_settings.FrameMs` | 管线作唯一事实源：Reconfigure 后回写并同步控件；UI 夹取范围改为 5–40 |
| 编码器竞态与泄漏 | `Reconfigure` 在 UI 线程就地改写编码线程正在使用的同一个 wrapper；重建分支不 Dispose 旧实例 | 参数变化一律新建编码器；旧实例延迟一代释放（`Retired`，两代后才 Dispose） |
| 编码线程无兜底 | `PumpLoop` 里订阅者回调抛异常会结束后台线程→进程 | 外层 `PumpGuard` 捕获并重启泵（记日志、不退出） |
| 超 MTU 分片（冗余同报文） | Opus 输出上限被设成 8 KB；`MaxOpusPayload=1275` 定义了却从未使用 | 编码输出限制到 1275 B；冗余在整包 >1400 B 时放弃 |
| 长会话延迟读数漂移 | `minRtt` 是整会话历史最小值，握手后即冻结 offset，而两端时钟各走（10–100 ppm） | 每 60 s 重置最小 RTT 窗口，让偏移重新收敛 |
| 格式热切换偶发杂音 | 播放线程在锁外读 `decoder/frameSamples/pcmOut/clockOffsetUs`，而接收线程会整体替换它们 | 锁内取一次自洽快照（局部变量）；时钟字段改 volatile |
| 指标刷新率 60 Hz 无效 | `metricsIntervalMs()` 有 50 ms 下限 | 下限改 16 ms，并让速率滑窗继续跟随（见 §10.7） |
