# 使用手册

## 一、准备

1. **同一局域网**：Windows 电脑与 Android 手机连接同一个 WiFi/路由器（不要用访客网络，客户端之间常被隔离）。
2. **安装两端**：
   - 下载：从 [Releases](https://github.com/XiaoliuNya/LanAudioStream/releases/latest) 获取 `LanAudioStream-1.0.0-win-x64.exe` 和 `LanAudioStream-1.0.0.apk`
   - 桌面端：直接双击 `LanAudioStream-1.0.0-win-x64.exe`（自包含，无需装 .NET）
   - 手机端：`adb install -r LanAudioStream-1.0.0.apk`，或把 APK 传到手机点击安装（需允许“安装未知来源应用”）
3. **防火墙**：首次运行桌面端时 Windows 会弹窗，勾选“专用网络”并允许。
   也可用管理员 PowerShell 执行：
   ```powershell
   powershell -ExecutionPolicy Bypass -File scripts\allow_firewall.ps1
   ```

## 二、桌面端操作

| 控件 | 说明 |
|---|---|
| 音频设备 | 默认“默认播放设备（推荐，跟随系统切换）”；也可指定某个扬声器 |
| **静音本机扬声器** | 勾选后本机不再出声，但**采集与串流照常进行**，手机端正常播放；取消勾选恢复原状态，程序退出时自动恢复 |
| 编码码率 | 64/96/128/160/192/256/320 kbps（VBR）。局域网建议 128–192 kbps |
| 帧长 | 5/10/20/40 ms。越短延迟越低、报文越密；**推荐 10 ms**；PCM 无损模式上限 10 ms |
| 端口 | 音频数据端口，默认 47655；发现端口固定 47654 |
| 采集缓冲 | 10/20/30/50 ms。越小延迟越低，过小在低配机器上可能爆音 |
| 抗丢包（重发上一帧） | 每个报文额外携带上一帧；丢一个包时可直接恢复，代价是带宽约翻倍 |
| 启动程序后自动开始串流 | 免手动点击 |
| **保存设置** | 把当前界面的设置应用到串流（运行中）并同步给手机端——**改完必须点它才生效** |
| **重置所有设置** | 所有设置项恢复默认值（只改本机界面），再点「保存设置」生效并同步到手机端 |

运行状态区（只显示电脑本机可直接得到的指标，不再显示任何需要手机回传的项目）：
- **客户端**：手机 IP:端口
- **会话状态**：监听中 / 已连接(待播) / 串流中
- **当前编码 / 采集设备**：当前编码格式与采集设备名
- **采集+编码延迟**：本机管线耗时
- **发送码率 / 发送包速率 / 累计发送**：本机 UDP 发送统计

> 想确认“手机听到的”确实是当前系统声音，请看手机端新增的**左右声道电平条**。

> 没有音频播放时，WASAPI Loopback 不会产生数据，因此“发送码率”为 0 属于正常现象。

## 三、手机端操作

1. 打开 App → 点击 **开始接收**
2. 状态变为“串流中”，指标、曲线与**左右声道电平条（L/R）**开始刷新（曲线与电平条按屏幕刷新率绘制，很跟手）
3. 需要后台播放时直接切到后台即可：前台服务会保持连接与播放，通知栏实时显示 延迟/码率/丢包
4. 音频设置分两组：**「音频设置（在电脑上生效）」改完必须点「保存设置」才会下发**；
   **「播放设置（本机）」改动立即生效**，其中抖动策略/自动重连会随「保存设置」一并同步给电脑端。
   点 **「重置所有设置」** 可一键恢复默认值，再点「保存设置」同步。
   实时曲线图位于设置界面上方，调参时可直接观察延迟/丢包变化。
   （低延迟模式、播放音量与开发者模式已移除：输出固定走默认媒体路径，保留系统音效。）
   本机设置里还有 **断连超时**（收不到音频多久重连，默认 8 秒）、**指标刷新率**（1–60 Hz）与
   **通知栏显示指标** 开关；数值型设置项都可以在列表里选「自定义…」直接输入数值。
5. 发现多个桌面端时，可用下拉列表选择后点“连接”

指标含义：

| 指标 | 含义 |
|---|---|
| 端到端延迟 | 桌面端采集到手机即将播放的总时间（时钟同步后计算） |
| 网络抖动 | RFC3550 式到达间隔抖动 |
| 接收码率 | 网络层接收速率（含包头与冗余；DTX 静音期会明显下降）。按**滑窗**统计，窗口长度＝指标刷新周期（默认 2 Hz→500 ms，最大 1 秒），随指标一起刷新 |
| 实时速度 | 音频负载的接收速率（不含包头/冗余），同样按**滑窗**统计，窗口长度＝指标刷新周期（不做平滑） |
| 丢包率 | 未恢复的丢帧比例 |
| 抖动缓冲 | 当前排队等待播放的音频时长 |
| 音频输出缓冲 | AudioTrack 内部尚未播放的时长 |
| PLC 补偿 | 用 Opus 丢包隐藏合成的帧数 |
| 播放欠载 | 缓冲被掏空、写入静音的次数（电脑端本来就没在放声音时不计入，只写静音） |
| 时钟同步 RTT | 与桌面端时钟同步的最小往返时延 |

## 四、参数建议

| 场景 | 建议 |
|---|---|
| 追求最低延迟（有线耳机） | 帧长 10 ms、码率 128 kbps、抖动策略「延迟优先」→ 端到端约 100–160 ms |
| 音质优先（听音乐，保留音效） | 帧长 20 ms、码率 192–256 kbps、抖动策略「自动」 |
| 网络不稳（丢包明显） | 打开“抗丢包（重发上一帧）”，或把码率降到 96 kbps |
| 功耗优先 | 帧长 20 ms、码率 96 kbps |

## 五、故障排查

| 现象 | 排查 |
|---|---|
| 手机一直“搜索桌面端” | ① 桌面端是否已点“开始串流”；② 两端是否同一网段（互相 `ping` 一下）；③ 防火墙是否放行 UDP 47654/47655；④ 路由器是否开启了“AP 隔离” |
| 连接上但没有声音 | 手机端“左右声道电平”是否有跳动；若为 0，说明系统当前没有播放音频 |
| 有声音但断续 | 关闭“抗丢包”试试（带宽翻倍可能压垮弱 WiFi）；把帧长调到 20 ms；靠近路由器 |
| 本机想静音但手机也没声音 | 请确认使用桌面端的“静音本机扬声器”开关，而不是在系统音量里静音**其它**设备；本工具的静音是端点静音，已验证不影响采集 |
| 延迟偏高 | 蓝牙耳机/音箱本身有 100–200 ms 固有延迟，换有线耳机测试可排除；也可在手机端把“抖动缓冲策略”改成“延迟优先” |
| 延迟随时间变大 | 抖动缓冲会按「真正饿死」自适应加深、比目标深时主动剪掉最旧帧回落（丢包走 PLC 不再抬高延迟，停播再把声音也不会把缓冲顶到上限）。界面日志里会打印 `缓冲 x→y ms（…）` 与 `缓冲过深，剪掉 N 帧`，可据此判断是谁在调 |
| 每隔几秒卡一下 | 看界面日志里的 10 秒汇总行：`网络停顿 3 次/10s（最大 286ms，最多成串 26 包）` —— 成串包数≈停顿毫秒数×0.1 说明包被整段压住后成串交付（WiFi 省电/DTIM，**没有丢包**），自动模式会把抖动缓冲加深到 ≈停顿+50ms 兜住（代价是延迟变大，想强制低延迟可设「延迟优先」，但会有可闻断音）；若成串包数≈0，那才是真丢包 |
| 手机锁屏后断流 | 检查系统是否限制了后台活动（部分国产 ROM 需在“电池/后台管理”中允许本应用后台运行） |
